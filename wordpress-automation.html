Markdown原稿からWordPressへ記事を一括公開する｜REST API × PowerShellの実装ガイド

納品した記事を1本ずつWordPressに貼り付けていくと、1記事あたり20〜30分、10本で半日が消えます。この記事は、Markdown形式で用意した原稿を、WordPress REST APIとPowerShellスクリプトで一括公開する仕組みを、認証から実装、運用の落とし穴までまとめたものです。ローカルの検証環境で動作確認した構成そのままを、現場で使える形で解説します。

1. WordPress入稿を自動化するべき3つの場面

WordPressの管理画面は、1本の記事を丁寧に仕上げるのに向いています。一方で、同じ作業が繰り返される局面では、手数の多さがそのまま納期と疲労に跳ね返ります。次の3つは、自動化の投資対効果が特に高い場面です。

場面1：オウンドメディアの大量入稿

月に20〜30本の記事を運用しているメディアでは、入稿作業そのものが「見出しタグ化・内部リンク・画像alt付与」といった定型作業の反復になります。1本あたり20分の作業時間でも、30本で10時間。ここが自動化対象の筆頭です。

場面2：ライターから納品されたMarkdown原稿の下書き化

最近は、ライター側がMarkdown形式で納品してくるケースが増えてきました。これをコピペで貼ると改行が崩れ、見出し構造も手で付け直すことになります。原稿をそのままREST API経由で下書き化すれば、エディタ側の調整は装飾の最後の仕上げだけで済みます。

場面3：記事の定期更新・リライト運用

既存記事の見出し構造だけ差し替える、本文末尾のCTAを一斉入れ替える、といった運用も、API経由なら数十記事を数分で処理できます。管理画面を1本ずつ開く作業は、ここでも省けます。

2. 構成の全体像と、使う技術スタック

今回紹介する仕組みは、特殊なサーバー構成を必要としません。ローカルのPC1台と、公開済みのWordPressサイトがあれば動きます。

要素採用した技術
原稿フォーマットMarkdown（.md）
実行環境PowerShell 5.1（Windows標準搭載）
認証方式WordPress Application Password（Basic認証）
投稿APIWP REST API（/wp-json/wp/v2/posts）
変換処理PowerShell内の正規表現ベース（追加ライブラリ不要）
補足：PowerShell以外にも、Python・Node.js・GAS など、HTTP POSTができる言語なら同じ構成が組めます。今回はWindows環境で追加インストール不要のPowerShellを採用しました。

3. 認証はApplication Passwordで統一する

WordPressにプログラムからアクセスする方法はいくつかありますが、WordPress 5.6以降はApplication Passwordが公式に用意されており、これを使うのが最も安全です。管理者パスワードを直接スクリプトに書く必要がなく、万が一流出した場合も、管理画面から当該のアプリケーションパスワードだけを無効化できます。

発行手順

  1. WordPress管理画面にログイン
  2. 「ユーザー」→「プロフィール」を開き、下部までスクロール
  3. 「アプリケーションパスワード」セクションで、名前（例：cli-automation）を入力
  4. 「新しいアプリケーションパスワードを追加」で、24桁のパスワードを発行
  5. 表示されたパスワードを控える（スペース込みでそのまま使用する）
注意：Application Passwordは発行直後の画面を閉じると二度と表示されません。必ずコピーして保管してください。ソースコードに直接書かず、環境変数や外部設定ファイルに逃がすのが本番運用の作法です。

4. Markdown原稿を投稿可能なHTMLに変換する

WordPress REST APIのcontentフィールドはHTMLを受け付けます。Markdownのままでは段落と見出しが崩れるので、最低限の変換を挟みます。

変換対象の最小セット

  • ## 見出し → <h2>見出し</h2>
  • ### 小見出し → <h3>小見出し</h3>
  • - リスト項目 → <ul><li>リスト項目</li></ul>
  • 空行で区切られたテキスト塊 → <p>...</p>

この4パターンだけでも、ブログ記事の9割はカバーできます。表やコードブロック、強調・リンクが必要になった時点で、同じ発想で変換ルールを足していけば十分です。

タイトルの扱い

Markdownの先頭にある# タイトルは、WordPress側のtitleフィールドに回します。本文の見出し階層とタイトルを混在させないことで、SEO上のh1重複も防げます。

5. PowerShellから REST API に POSTする実装

認証ヘッダーの作り方と、投稿APIの呼び出し方は、次の3ステップで整理できます。

ステップ1：Basic認証ヘッダーの生成

$pair    = "${WP_USERNAME}:${WP_APP_PASS}"
$encoded = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes($pair))
$headers = @{
    'Authorization' = "Basic $encoded"
    'Content-Type'  = 'application/json; charset=utf-8'
}

ユーザー名とApplication Passwordを:で結合し、Base64エンコードしてAuthorizationヘッダーに乗せるだけです。Application Passwordに含まれるスペースは、そのまま残してください（除去すると認証が通りません）。

ステップ2：投稿データの組み立て

$postData = @{
    title   = $title
    content = $htmlBody
    status  = 'draft'   # 'publish' で即公開
} | ConvertTo-Json -Depth 10

最初はdraftで下書きとして投稿し、管理画面で最終確認してから公開ボタンを押す運用が安全です。確認が不要な定型記事では、直接publishを指定します。

ステップ3：POSTの実行

$endpoint = "$WP_URL/wp-json/wp/v2/posts"
$bytes    = [Text.Encoding]::UTF8.GetBytes($postData)
$response = Invoke-RestMethod -Uri $endpoint -Method Post `
                              -Headers $headers -Body $bytes

Write-Host "Post ID: $($response.id)"
Write-Host "URL: $($response.link)"

日本語本文を正しく送るため、JSON文字列をUTF-8のバイト列に変換してからBodyに渡しています。Invoke-RestMethodは返却されたJSONを自動でオブジェクト化するので、投稿ID・URL・ステータスをそのまま変数から取り出せます。

6. 運用で押さえておきたい3つの落とし穴

仕組みが動いた後、現場で詰まりやすいのは次の3点です。

落とし穴1：認証エラーは、ほぼスペースの扱いが原因

「401 Unauthorized」が返ってくる場合、Application Passwordからスペースを削ってしまっているケースが大半です。発行時に表示された文字列を、スペースも含めてそのまま貼り付けるのが正解です。

落とし穴2：ユーザー名は「表示名」ではなく「ログインID」

WordPressではニックネーム・表示名・ユーザー名が別物です。REST APIで使うのは、ログイン時に入れているユーザー名（user_login）です。管理画面の「ユーザー」一覧で、該当アカウント行の「ユーザー名」列を確認してください。

落とし穴3：いきなり「公開」で走らせない

スクリプトのバグで、意図しない記事が公開されてしまうと戻すのに時間がかかります。実運用に乗せる前は、必ずdraftで動作確認し、タイトル・本文・ステータス・パーマリンクを管理画面で見て、問題がなければpublishに切り替える。この一手間が、事故を未然に防ぎます。

拡張の余地：この基本構成の上に、アイキャッチ画像のメディアアップロード、カスタムフィールド、カテゴリ・タグの自動付与、既存記事の一括更新といった機能を少しずつ足せます。REST APIが対応する範囲なら、構造は変えずに積み上げられます。
本記事の免責事項：本記事は検証環境で動作確認した一般的な実装例を解説したものであり、特定のWordPress環境・プラグイン構成での動作を保証するものではありません。本番環境への適用前には、必ずテスト環境で動作検証を行ってください。Application Passwordを含む認証情報は、ソースコードに直接記載せず、環境変数や暗号化された外部ストアで管理することを推奨します。
